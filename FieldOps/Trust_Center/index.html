Security posture, permissions, data handling, and how to report a vulnerability.

Authentication model

FieldOps never asks for API tokens or passwords. On the phone, people sign in with Atlassian's OAuth 2.0 (3LO), through Atlassian's own login pages, with or without SSO. The integration is resource-level: the token only works on the site the person picks during sign-in. Every Jira call is made with that person's token, so Jira itself decides what they can see and do.

The settings page runs inside Jira on Atlassian Forge, and every backend call checks that the signed-in user is a Jira administrator.

Scopes

Mobile app (OAuth 2.0)

  • read:jira-work, read:jira-user: read the tickets, fields, comments and attachments the person can see, and the person's name.
  • read:servicedesk-request: read requests, Forms and approvals.
  • read:cmdb-object:jira: read the Assets attributes chosen by the admin.
  • write:jira-work: add comments, change the status (transitions), fill in the fields of the transition screen and upload attachments.
  • write:servicedesk-request: answer approvals, and add comments and attachments to requests as internal or visible to the customer.
  • offline_access: renew the sign-in without asking for the password again, while the session lasts.

Settings app (Forge)

  • read:jira-work, read:project:jira, read:issue-type:jira, read:field:jira, read:servicedesk-request: list projects, issue types, request types and fields for the layout editor.
  • read:project.property:jira, write:project.property:jira: read and save layouts as project properties.
  • read:permission:jira: check that the user is a Jira admin.
  • read:cmdb-object:jira, read:cmdb-type:jira, read:cmdb-attribute:jira: list Assets attributes for the layout editor.

Data protection

  • All traffic uses HTTPS.
  • Sign-in sessions, including Atlassian tokens, are encrypted with AES-GCM before they are stored. Tokens are never sent to the browser.
  • The session cookie is random, HttpOnly, Secure and SameSite=Lax, and lasts up to 12 hours. A new session ID and security token are created at every sign-in.
  • Every action that changes data (comments, transitions, attachments and approvals) requires a per-session security token against forged requests.
  • Uploads accept only images, PDF, text and Office files, up to 6 MB each, with a limit per minute. Files go straight to Jira and are not stored by FieldOps.
  • Ticket content and attachments are not stored by FieldOps. Assets attributes not chosen by the admin never reach the phone.
  • The app does not track the device location.

Site isolation and activation

  • Only sites activated by a Jira admin can sign in. Activation is sent from the FieldOps app in Jira to the backend through Forge Remote, with a token signed by Atlassian that the backend verifies.
  • Admins can deactivate FieldOps at any time in the settings page. Uninstalling the app also disables the site.
  • If the backend stops hearing from the app installed in Jira for 48 hours, the site is disabled automatically.
  • Admins can block or remove FieldOps for the whole organization in admin.atlassian.com > Connected apps.

Infrastructure

  • Settings app: Atlassian Forge.
  • Mobile backend: Cloudflare Workers, with sessions and site records in Cloudflare D1 (primary region: Eastern North America).
  • Because the mobile app runs outside Atlassian, FieldOps is not eligible for the Runs on Atlassian program.

Development practices

  • Code is versioned on GitHub, and every change goes through a pull request with automated tests before it is merged.
  • Changes are tested in a separate staging environment before reaching customers.
  • Secrets live only in the hosting platform, never in the code.

Report a vulnerability

If you find a security problem, write to support@app-rl.com with the steps to reproduce it. We reply as soon as possible and keep you updated until it is fixed. Please do not share the details publicly before the fix.

Modelo de autenticação

O FieldOps nunca pede token de API nem senha. No celular, as pessoas entram pelo OAuth 2.0 (3LO) da Atlassian, nas páginas de login da própria Atlassian, com ou sem SSO. A integração é resource-level: o token só vale pro site que a pessoa escolhe no login. Toda chamada ao Jira é feita com o token dessa pessoa, então o próprio Jira decide o que ela pode ver e fazer.

A página de configurações roda dentro do Jira, no Atlassian Forge, e toda chamada ao backend confere se o usuário logado é administrador do Jira.

Escopos

App do celular (OAuth 2.0)

  • read:jira-work, read:jira-user: ler os chamados, campos, comentários e anexos que a pessoa pode ver, e o nome dela.
  • read:servicedesk-request: ler solicitações, Forms e aprovações.
  • read:cmdb-object:jira: ler os atributos do Assets escolhidos pelo admin.
  • write:jira-work: comentar, mudar o status (transições), preencher os campos da tela de transição e enviar anexos.
  • write:servicedesk-request: responder aprovações e incluir comentários e anexos nas solicitações, como internos ou visíveis pro cliente.
  • offline_access: renovar o login sem pedir a senha de novo, enquanto a sessão durar.

App de configurações (Forge)

  • read:jira-work, read:project:jira, read:issue-type:jira, read:field:jira, read:servicedesk-request: listar projetos, tipos de issue, request types e campos no editor de layout.
  • read:project.property:jira, write:project.property:jira: ler e salvar os layouts como propriedades do projeto.
  • read:permission:jira: conferir se o usuário é admin do Jira.
  • read:cmdb-object:jira, read:cmdb-type:jira, read:cmdb-attribute:jira: listar os atributos do Assets no editor de layout.

Proteção dos dados

  • Todo o tráfego usa HTTPS.
  • As sessões de login, incluindo os tokens da Atlassian, são criptografadas com AES-GCM antes de serem salvas. Os tokens nunca vão pro navegador.
  • O cookie de sessão é aleatório, HttpOnly, Secure e SameSite=Lax, e dura até 12 horas. A cada login são criados um novo ID de sessão e um novo token de segurança.
  • Toda ação que altera dados (comentários, transições, anexos e aprovações) exige um token de segurança por sessão, contra requisições forjadas.
  • Os uploads aceitam só imagens, PDF, texto e arquivos do Office, até 6 MB cada, com limite por minuto. Os arquivos vão direto pro Jira e não são guardados pelo FieldOps.
  • O FieldOps não guarda conteúdo de chamados nem anexos. Atributos do Assets que o admin não escolheu nunca chegam no celular.
  • O app não rastreia a localização do aparelho.

Isolamento e ativação dos sites

  • Só sites ativados por um admin do Jira conseguem entrar. A ativação vai do app FieldOps no Jira pro backend pelo Forge Remote, com um token assinado pela Atlassian que o backend confere.
  • Os admins podem desativar o FieldOps quando quiserem, na página de configurações. Desinstalar o app também desativa o site.
  • Se o backend ficar 48 horas sem notícia do app instalado no Jira, o site é desativado automaticamente.
  • Os admins podem bloquear ou remover o FieldOps da organização toda em admin.atlassian.com > Connected apps.

Infraestrutura

  • App de configurações: Atlassian Forge.
  • Backend do celular: Cloudflare Workers, com sessões e cadastros de site no Cloudflare D1 (região principal: leste da América do Norte).
  • Como o app do celular roda fora da Atlassian, o FieldOps não é elegível ao programa Runs on Atlassian.

Práticas de desenvolvimento

  • O código é versionado no GitHub, e toda mudança passa por pull request com testes automáticos antes do merge.
  • As mudanças são testadas num ambiente de homologação separado antes de chegar aos clientes.
  • Os secrets ficam só na plataforma de hospedagem, nunca no código.

Reportar uma vulnerabilidade

Se você encontrar um problema de segurança, escreva pra support@app-rl.com com os passos pra reproduzir. A gente responde o quanto antes e te mantém informado até a correção. Por favor, não divulgue os detalhes publicamente antes da correção.
